# Git Bash 下执行 Windows 原生命令需用 cmd //c 阻止 MSYS 路径转换

## Scenario
在 Windows 上通过 Git Bash（MSYS）执行 Windows 原生命令（taskkill/tasklist 等）或经 bash 包装 PowerShell 命令时，命令参数被意外改写导致失败；在 PowerShell 中试图用 `&` 后台启动服务时报解析错误。

## Key Signals
- `taskkill /F /IM python.exe` 报 **"ERROR: Invalid argument/option - 'F:/'"**——MSYS 把 `/F` 开关误当 POSIX 路径，转换成了 `F:/`。
- `tasklist /FI "..."` 报 "Invalid argument/option - 'C:/Program Files/Git/IM'"——`/FI` 被转换成 Git 安装路径。
- PowerShell 中 `... > /tmp/x.log 2>&1 &` 报 **AmpersandNotAllowed**——`&` 是 PowerShell 保留运算符。
- bash 双引号包裹 `powershell -Command "...$var..."` 时 `$var` 被 bash 先展开，破坏 PowerShell 命令。

## Essence
MSYS（Git Bash 底层）对以 `/` 开头的参数做 POSIX→Windows 路径自动转换，Windows 命令的开关参数（/F、/IM、/FI）全部遭殃；PowerShell 的语法规则与 bash 不同（`&` 是保留字、变量在双引号中展开）。两个 shell 的转义规则不可混用，必须显式阻断转换或用原生包装层。

## Approach
1. **MSYS 下执行 Windows 原生命令**：用 `cmd //c` 包装，双斜杠阻止 MSYS 转换：
   ```bash
   cmd //c "taskkill /F /IM python.exe"
   cmd //c "tasklist | findstr python"
   ```
2. **需要 PowerShell 时**：`-Command` 参数用**单引号**包裹，阻止 bash 展开 `$` 变量：
   ```bash
   powershell -Command '$PSVersionTable.PSVersion.ToString()'
   ```
3. **PowerShell 中后台启动服务**：不用 `&`，改用 `Start-Process` 或经 cmd 启动；bash 下用 `nohup ... &` 或后台重定向。
4. 复杂进程管理（枚举+批量终止）写成临时脚本文件执行，避免行内转义地狱。

## Faster Next Time
- 看到 "Invalid argument/option - 'X:/'"（X 为单字母盘符）先想到 MSYS 路径转换，立即换 `cmd //c` 包装。
- 含 `/` 开关的 Windows 命令在 Git Bash 中一律先 `cmd //c` 包装，不要裸执行。
- PowerShell 命令含 `$` 时只用单引号包裹。

## Applicability Boundaries
- 适用：Windows + Git Bash/MSYS 终端混合执行 Windows 原生命令；bash 包装 PowerShell 的场景。
- 不适用：原生 Linux/macOS 环境（无 MSYS 转换）；纯 PowerShell 或纯 cmd 会话内执行本 shell 命令。

## Evidence or Examples
- 失败：`taskkill /F /IM python.exe` → "ERROR: Invalid argument/option - 'F:/'"。
- 失败：`tasklist /FI "..."` → "Invalid argument/option - 'C:/Program Files/Git/IM'"。
- 失败：PowerShell 行内 `> /tmp/x.log 2>&1 &` → AmpersandNotAllowed 解析错误。
- 成功：`cmd //c "taskkill /F /IM python.exe"` 依次终止 7 个残留 python 进程。

# 中文长查询检索返回空时用滑动窗口提取 2-4 字子串关键词

## Scenario
为中文知识库构建关键词检索（SQLite FTS5 / 正则提取查询关键词）时，单个短词查询正常，但用户输入完整中文长句（如"校园巴士运行线路怎么走"）后检索返回 0 结果。

## Key Signals
- 短词查询（"选课"、"巴士"）能命中，完整长句查询返回空——说明数据在、检索逻辑通，问题出在查询处理。
- 调试打印关键词集合，发现长句只产出 **一个** 元素：`{'校园巴士运行线路怎么走'}`——整个连续中文被当成一个 token。
- 曾误以为是 API 进程缓存问题（实际另案），先排除。

## Essence
三个反直觉机制叠加导致失效：
1. `re.findall(r"[\u4e00-\u9fff]{2,}", query)` 贪婪匹配，把连续中文整串作为一个 token，长句产不出任何可用关键词。
2. FTS5 默认 unicode61 分词器把连续中文当一个 token，中文查询在 FTS5 内天然失效。
3. trigram 分词器要求 token ≥3 字符，对 2 字中文词（"校巴"、"电话"）完全无效。
4. 网络受限环境下 jieba 安装可能超时，需要无外部依赖的降级方案。

## Approach
1. 中文关键词不用正则一次性提取，改用**滑动窗口**遍历查询串，提取全部 2-4 字纯中文子串作为关键词候选：
   ```python
   for i in range(len(query)):
       for n in (2, 3, 4):
           sub = query[i:i+n]
           if re.match(r"[\u4e00-\u9fff]+$", sub):
               keywords.add(sub)
   ```
2. 叠加**同义词表扩展**（如"校巴"→["班车","巴士","校车"]），提升召回。
3. FTS5 全文索引只负责**数字/英文 token**（电话号码、CET 等缩写），用 bm25 排序。
4. 中文匹配走 **LIKE 子串匹配**（对中文天然按字符切分，长句可用）。
5. 按字段加权计分（标题命中权重高于正文），合并多路结果排序。

## Faster Next Time
- 长查询返回空时，第一步先打印关键词集合，确认 token 是否被整串吞掉——一条调试输出即可定位方向。
- 引入 FTS5 前先用 2 字中文词验证分词器行为，不要默认它对中文可用。
- 无 jieba 时不必阻塞：LIKE 子串 + 滑动窗口关键词是可用的降级路径。

## Applicability Boundaries
- 适用：无外部分词依赖的中文关键词检索、中小规模数据（万级以内 LIKE 可接受）。
- 不适用：已能安装 jieba/pkuseg 等分词器的场景（分词效果优于滑动窗口）；超大规模数据（LIKE 全表扫描成为瓶颈）；纯语义检索场景。

## Evidence or Examples
- 修复前：「校园巴士运行线路怎么走」→ 0 结果；`_extract_keywords` 输出 `{'校园巴士运行线路怎么走'}`（单一整串）。
- 修复后：同一查询返回 3 条结果，top1 score 54（标题完全匹配的"关于校园巴士运行线路调整的通知"）。
- trigram 验证：对"校巴/巴士/班车/电话/报修/选课"全部返回 `[]`，证实 2 字词失效。
- jieba `pip install` 超过 120s 超时，最终放弃，改走混合方案。

# 官网爬虫解析三类陷阱：全局选择器误抓导航、同 CMS 模板差异、正文为空与零宽字符

## Scenario
为多个校园/机构官网（苏迪 sudy 等 CMS 搭建的站点）抓取通知列表页与详情页，构建问答知识库。站点多、模板杂，静态 HTML 抓取。

## Key Signals
- **误抓导航**：入库数据出现"教学日历"等导航条目——全局 `a[title]` 选择器把左侧导航链接（也含 `/page.htm` 链接）误判成文章。
- **同 CMS 不同模板**：同一苏迪 CMS 下，教务处列表页用 `table.wp_article_list_table`，后勤处用 `a.column-news-item`（标题在 `span.column-news-title`），招生办是无标准分页的静态 page——同一套选择器在不同站点解析失败。
- **正文为空**：核心文档（服务电话、报修办法）`content` 长度为 0——正文是图片（3 个 img 无 alt）或前端动态加载，静态抓取拿不到。
- **零宽字符**：标题混入 U+200B（`\u200b校内各类故障报修办法`），导致后续精确匹配/子串匹配失败。

## Essence
1. 列表页解析必须**限定在文章列表容器内**，任何全局属性选择器都会把导航、页眉链接一并抓入。
2. 不能假设"同一 CMS = 同一模板"：解析器需按模板分支适配（表格列表 / 卡片列表 / 静态单页），先人工查看目标页 HTML 结构再写选择器。
3. 静态抓取天然拿不到图片正文与动态加载内容：入库时检测空 content，打分时补偿（标题命中加权），并把此类文档记为已知缺口（后续用无头浏览器渲染或人工补录）。
4. 网页文本常混入零宽字符（U+200B/U+200C/U+200D/U+FEFF），清洗阶段统一移除，否则污染下游精确匹配。

## Approach
1. 写选择器前先人工抓取并查看列表页/详情页 HTML，确认文章列表容器的 class。
2. 解析范围限定在列表容器（如 `table.wp_article_list_table`）内，而非全局 `a[title]`。
3. 为不同站点/模板分别定义解析分支（表格型 / 卡片型 / 静态页型），配置驱动。
4. 入库前校验每条数据字段完整性（标题/正文/时间/URL），统计 content 长度分布，空正文打补偿分并记缺口。
5. 清洗函数统一执行：去 HTML 标签、br/p 转换行、压空白、移除零宽字符。

## Faster Next Time
- 首批小批量试跑后先**抽查入库数据的标题列表**，一眼即可发现导航误抓。
- 用 `repr()` 检查标题，零宽字符等不可见字符立现。
- 入库后统计 content 长度为 0 的文档占比，及早发现动态加载/图片正文缺口。
- 多站点接入时先确认是否同 CMS，再确认列表页模板是否相同——两者都要逐一验证。

## Applicability Boundaries
- 适用：静态 HTML 爬虫、传统 CMS（苏迪/博达等）站点、多站点批量抓取。
- 不适用：纯 SPA 站点（需无头浏览器渲染）；已有结构化数据接口（API/RSS）的站点。

## Evidence or Examples
- 误抓实例：全局 `a[title]` 把导航"教学日历"入库；限定 `table.wp_article_list_table` 后消失。
- 空正文实例：「校内日常服务电话」「校内各类故障报修办法」content 长度 0，原页面正文为 3 个 img（无 alt 文本），判定为动态加载/图片正文，记为已知缺口。
- 零宽字符实例：标题 repr 为 `'\u200b校内各类故障报修办法'`，清洗函数移除 `[\u200b\u200c\u200d\ufeff]` 后恢复正常。
- 模板差异实例：教务处 `table.wp_article_list_table`、后勤处 `a.column-news-item` + `span.column-news-title/date`、招生办静态 policy page，三套分支适配后全部跑通。

# 改了代码但 HTTP 接口行为不变时先查残留的旧服务进程

## Scenario
开发 Python Web 服务（uvicorn/FastAPI 等，未开 `--reload`）时，修改了检索逻辑并确认源码已更新，但通过 HTTP 调用接口仍然返回旧结果或空结果；反复修改代码无效果。

## Key Signals
- **强信号**：直接在 Python 里调用同一个函数返回正确结果，而通过 HTTP 调用返回空/旧结果——代码和数据都没问题，问题必然在"运行中的进程"层面。
- 源码 mtime 确认为新版本、数据库内容确认正确后，HTTP 行为依旧异常。
- 列出进程发现 **7 个 python.exe** 同时在跑——此前多次后台启动的服务实例全部残留，占用同一端口。

## Essence
根因链：多次后台启动服务且未彻底终止 → 多个旧进程残留并占用端口 → 新请求打到缓存旧代码的旧进程上 → "改了代码但接口行为不变"的假象。症状表现在 HTTP 层，根因在进程管理层；定位方向应从代码逻辑转向运行时进程状态。

## Approach
排查优先顺序（先便宜后昂贵，先逻辑后运行时）：
1. **直接调用函数**验证核心逻辑——正常则排除代码本身。
2. 确认源码已保存（mtime、diff）——排除文件未落盘。
3. 确认数据与配置路径——排除数据问题。
4. **列出 python 进程**：`tasklist | findstr python`（Windows）或 `ps aux | grep python`，确认是否有多个残留实例。
5. 全部终止旧进程后重启单一服务实例，重新验证接口。
6. 注意：Git Bash 下 taskkill 参数会被路径转换破坏（详见关联经验），需用 `cmd //c "taskkill /F /IM python.exe"` 或等价方式执行。

## Faster Next Time
- 改代码后行为不变，第一反应查进程列表而不是继续改代码——这一步最便宜且命中率最高。
- 启动服务采用"先杀后启"习惯：每次启动前先终止旧实例。
- 验证链路时优先用"直接调用函数 vs HTTP 调用"做对照实验，一次对比即可把问题空间一分为二。

## Applicability Boundaries
- 适用：uvicorn/FastAPI/gunicorn/Flask 等常驻 Python 服务（未开热重载）；任何"代码已改但行为未变"的常驻服务场景。
- 不适用：已开 `--reload` 的开发模式；进程管理由容器/编排平台负责的场景（应查容器重启策略）。

## Evidence or Examples
- 排查过程中 HTTP `/ask` 对长查询持续返回空（confidence 0.0、refs 0），而直接调用 `search()` 返回 66 条评分结果。
- `tasklist` 输出 7 个 python.exe（PID 17612/2956/5720/29524/29476/28044/7164）。
- 全部终止后重启单一实例，同一长查询立即返回 confidence 1.0 与正确引用。

# 检索评测命中判定需与期望标注格式匹配，用核心子串模糊匹配而非全句包含

## Scenario
为检索问答系统建立自动评测（CSV 评测集 + 运行器），期望答案要点标注为自由文本，命中判定用子串包含。出现明显命中的题目（置信度 1.0、标题完全匹配）被评测判为未命中的假阴性。

## Key Signals
- 第 4 题"四六级考试什么时候报名"conf=1.0 且返回标题正确，却被判未命中——检索对了、判定错了。
- 期望标注是完整句子（"四六级考试报名时间与流程"），判定逻辑按"、"分隔后只有一个超长关键词，全句子串在答案/标题中不存在——**假阴性**。
- 修正判定后准确率从 62.5% → 75% → 100%（40 问），全程检索逻辑未变。

## Essence
评测判定的宽松度必须与标注格式匹配：
1. 期望标注写成完整句子时，"全句子串包含"判定必然产生大量假阴性——句子无法逐字出现在系统输出中。
2. 正确做法：判定用**核心子串模糊匹配**——按"、"分隔关键词；无分隔符时用 2-4 字滑动窗口提取核心子串；任一核心子串命中答案或标题即算命中（或按命中比例阈值 ≥30% 判定）。
3. 打分/判定调整前后需先人工核对若干条判定结果，校准宽松度，避免从"过严"摆到"过松"。

## Approach
1. 评测集格式先规范：期望答案要点按"、"分隔为关键词列表（标注约定写进列说明）。
2. 判定逻辑三层兜底：按"、"分隔 → 无分隔符时滑动窗口提取 2-4 字核心子串 → 任一子串命中答案/标题即命中。
3. 引入命中比例阈值（如 ≥30% 子串命中）防止完全无关内容误命中。
4. 每次调整判定后先抽查"命中但判未命中"和"未命中判命中"两类样例，校准后再跑全量。
5. 打分与判定分离：检索打分（标题加权、空正文补偿）影响置信度，判定只关心是否命中预期内容。

## Faster Next Time
- 评测准确率异常低时，先找一条"人工判断命中但评测判未命中"的样例，对比判定关键词——一条样例即可定位判定逻辑问题。
- 评测集建集时同步约定标注格式（分隔符、关键词粒度），避免标注与判定各自演化。
- 判定结果输出保留中间量（提取出的关键词、命中了哪个子串），便于事后审计。

## Applicability Boundaries
- 适用：关键词命中类自动评测（子串包含判定）；检索问答系统的快速回归评测。
- 不适用：语义相似度评测（embedding 相似度判定不受标注格式影响）；需要严格答案等价判定的场景（应人工评审或语义判定）。

## Evidence or Examples
- 判定修正前：40 问中第 4 题 conf=1.0 且标题匹配仍判未命中（期望"四六级考试报名时间与流程"全句子串不存在于输出）。
- 判定修正过程：6/8（75%）→ 修正滑动窗口 + 标题加权后 8/8（100%）→ 扩充 40 问全命中（100%）。
- 附带教训：评测题第 14/15 题出现"英语专业四级"误匹配"朝鲜语专业四级"——子串模糊匹配偏宽松，需配合更精确的类别过滤或语义判定（已在边界中标注）。
