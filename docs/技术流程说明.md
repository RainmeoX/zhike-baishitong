> 面向珠海科技学院 3.1 万在校生的校务生活 RAG 智能问答平台。

## 2. 数据层

### 2.1 数据采集

三个爬虫分别采集珠海科技学院三个官方站点的公开通知：

| 爬虫 | 站点 | 采集内容 | 文档数 |
|---|---|---|---|
| `crawler/jiaowu` | 教务处 | 选课、考试、学籍、毕业等通知 | 109 篇 |
| `crawler/houqin` | 后勤处 | 报修、餐饮、住宿、通勤等通知 | 87 篇 |
| `crawler/zsb` | 招生网 | 分数线、录取、奖学金、新生等通知 | 90 篇 |

**爬虫礼仪**：请求间隔 ≥5 秒、带 UA 和 Referer、只爬公开通知页面。

### 2.2 数据字段

每篇通知入库字段统一为：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | TEXT | 文档唯一标识 |
| `title` | TEXT | 通知标题 |
| `source_url` | TEXT | 原文链接 |
| `publish_time` | TEXT | 发布时间（YYYY-MM-DD） |
| `publisher` | TEXT | 发布者 |
| `department` | TEXT | 所属部门 |
| `column_name` | TEXT | 栏目名称 |
| `content` | TEXT | 正文内容 |
| `crawled_at` | TEXT | 爬取时间 |

### 2.3 数据存储

- **主表**：`documents`，SQLite 单表存储所有字段

**当前数据规模**：286 篇通知（教务 109 + 后勤 87 + 招生 90）。

## 3. 检索层（核心）

检索层是整个系统的核心，采用**混合检索**策略：关键词路 + 语义路并行，RRF 融合后重排精排，最后时效降权。

### 3.1 检索全流程

```
学生提问
  │
  ├─① 关键词路（FTS5 + LIKE + 同义词）───→ top-K 候选
  │                                        │
  ├─② 语义路（bge-m3 embedding）────────→ top-K 候选
  │                                        │
  ├─③ RRF 融合（基于排名合并两路）─────→ top-2K 候选
  │                                        │
  ├─④ Rerank 精排（bge-reranker-v2-m3）─→ 重排
  │                                        │
  ├─⑤ 时效降权（年份权重衰减）─────────→ 最终排序
  │                                        │
  └────────────────────────────────────→ top-K 返回
```

### 3.2 关键词路（`retrieval/search.py`）

**目标**：精确匹配字面关键词，保证数字、英文、专有名词必中。

**三步流程**：

#### 步骤 1：同义词扩展

维护 52 组珠科特色同义词表（`SYNONYMS` 字典），将学生口语扩展为通知用语：

```
"四六级" → ["四、六级", "四级", "六级", "CET"]
"准考证" → ["考试证", "打印准考证"]
"报修电话" → ["服务电话", "联系电话", "后勤电话", "日常服务"]
"空调" → ["风扇", "空调清洗"]
```

覆盖交通、餐饮、住宿、缴费、报修、教务、招生、后勤、安全、体测等 10 个主题域。

#### 步骤 2：FTS5 全文检索

提取查询中的数字和英文 token（≥2 字符），构建 FTS5 MATCH 查询：

```sql
SELECT doc_id, bm25(documents_fts) AS r
FROM documents_fts
WHERE documents_fts MATCH '"CET" OR "四级" OR "准考证"'
ORDER BY r
LIMIT 30
```

- 使用 BM25 算法排序（词频高、文档短的排前面）
- 命中文档加 10 分基础分

#### 步骤 3：LIKE 中文子串匹配

FTS5 对中文分词不完美，用 LIKE 兜底做子串匹配：

```sql
SELECT doc_id, title, content FROM documents
WHERE title LIKE '%准考证%' OR content LIKE '%准考证%'
```

打分规则：
- 标题命中：+6 分
- 正文命中：+1 分
- 标题命中但正文为空（图片/表格页）：额外 +4 分

**特点**：毫秒级、本地免费、精确匹配，但无法理解语义（"空调坏了"搜不到"维修电话"）。

### 3.3 语义路（`retrieval/embedding.py` + `retrieval/vector.py`）

**目标**：基于语义相似度检索，解决关键词路无法覆盖的同义/近义问题。

#### Embedding 向量化

调用华为云 MaaS bge-m3 模型，将文本转为 1024 维浮点向量：

```
"宿舍空调坏了怎么报修" → [0.12, -0.45, 0.78, ..., 0.33]  （1024 维）
"空调故障报修联系电话" → [0.11, -0.43, 0.80, ..., 0.35]  （语义相近，向量相近）
"食堂今天吃什么菜"     → [0.89, 0.22, -0.15, ..., -0.67] （语义无关，向量差异大）
```

- **建库时**：286 篇通知的 `title + content`（截取前 1500 字）批量调 bge-m3 转向量，存入 `vectors.db`
- **查询时**：学生问题转向量，与 286 个文档向量逐一计算余弦相似度

#### 余弦相似度计算

```python
def cosine(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    na = sum(x * x for x in a) ** 0.5
    nb = sum(y * y for y in b) ** 0.5
    return dot / (na * nb) if na and nb else 0.0
```

286 篇规模下暴力余弦计算 <10ms，无需 FAISS 等近似最近邻库。

**特点**：能理解语义同义/近义，但精度较粗（双向编码，query 和 doc 分别编码后算距离）。

### 3.4 RRF 融合（`retrieval/hybrid.py`）

**问题**：关键词路分数（如 17 分）和语义路分数（如 0.87）量纲不同，无法直接比较合并。

**RRF（Reciprocal Rank Fusion）**：不看分数，只看排名，用倒数公式融合：

```
RRF_score(doc) = Σ  1 / (K + rank_i + 1)
                 路i
```

其中 K=60（经验常数），rank_i 是文档在第 i 路检索中的排名（从 0 开始）。

**示例**：

```
关键词路排名：              语义路排名：
  rank 0: 文档A → 0.0164      rank 0: 文档C → 0.0164
  rank 1: 文档B → 0.0161      rank 1: 文档A → 0.0161
  rank 2: 文档C → 0.0159      rank 2: 文档B → 0.0157

融合后：
  文档A：0.0164 + 0.0161 = 0.0325  ← 两路都排前列，最高
  文档C：0.0159 + 0.0164 = 0.0323
  文档B：0.0161 + 0.0157 = 0.0318
```

**核心优势**：
- 量纲无关：只用排名，两路分数不需要归一化
- 双路命中加权：两路都出现的文档分数叠加，最可能是正确答案
- 单路独占保留：只在一路出现的文档不丢弃，分低但仍参与候选

### 3.5 Rerank 精排（`retrieval/rerank.py`）

**问题**：embedding 是双向编码（query 和 doc 分别转向量再算距离），精度有限。初筛结果可能排序不准。

**Rerank**：用交叉编码器（Cross-Encoder）对 query 和 doc 联合编码，精度远高于 embedding。

调用华为云 MaaS bge-reranker-v2-m3：

```python
body = {
    "model": "bge-reranker-v2-m3",
    "query": "宿舍空调坏了怎么报修",
    "documents": ["后勤处维修电话通知...", "水电维修流程通知..."],
}
# 返回每个 doc 的 relevance_score，按分数重排
```

**与 embedding 的区别**：

| | Embedding (bge-m3) | Reranker (bge-reranker-v2-m3) |
|---|---|---|
| 编码方式 | 双向编码（Bi-Encoder） | 交叉编码（Cross-Encoder） |
| query 和 doc | 分别编码后算距离 | 拼接后联合编码 |
| 精度 | 较粗 | 精细 |
| 速度 | 快（能扫 286 篇） | 慢（只对候选池做） |
| 用途 | 初筛 | 精排 |

**空内容文档特殊处理**：图片/表格页正文为空，reranker 无法有效评估，代码中对其提高 RRF 权重（0.2×rerank + 0.8×RRF），正常文档则 0.65×rerank + 0.35×RRF。

### 3.6 时效降权（`retrieval/hybrid.py`）

校务通知有强时效性，旧通知可能已过期。按发布年份衰减权重：

```python
def _recency(d):
    y = int(d["publish_time"][:4])
    if y >= current_year:   return 1.0   # 当年通知
    if y == current_year-1: return 0.75  # 去年通知
    return 0.5                          # 更早通知
```

**最终分数** = `blended_score × recency_weight`

### 3.7 最终排序公式

```
final_score = (w_rerank × rerank_score + w_rrf × rrf_normalized) × recency_weight

其中：
  正常文档：w_rerank=0.65, w_rrf=0.35
  空内容文档：w_rerank=0.2, w_rrf=0.8
  rrf_normalized = rrf_score / max_rrf_score
  recency_weight: 当年=1.0, 去年=0.75, 更早=0.5
```

## 4. 生成层（`api/llm.py`）

### 4.1 LLM 生成流程

检索拿到 top-K 文档后，送入大模型生成自然语言回答：

```
top-K 文档 + 学生问题 → 构建 prompt → 调 GLM-4-Flash → 口语化回答 + 来源标注
```

### 4.2 Prompt 构建

**System Prompt**（约束模型行为）：

```
你是「珠科百事通」校务问答助手，服务珠海科技学院 3.1 万在校生。
回答规则：
1. 用口语化、简洁的方式回答，像学长学姐给同学解答一样自然
2. 严格基于【参考内容】回答，不编造、不补充参考内容以外的信息
3. 回答末尾标注来源，格式：「（来源：部门-通知标题）」
4. 如果参考内容不足以回答，明确说明并建议联系相关部门
5. 涉及电话、时间、金额等关键信息，逐字引用原文，不改写
```

**User Prompt**（注入检索结果）：

```
【参考内容】
[1] 部门：后勤处 | 标题：校内日常服务电话
后勤处日常服务电话：0756-7626267，受理水电维修、家具报修等服务。

[2] 部门：后勤处 | 标题：维修服务流程
维修申请可通过官网提交或电话报修...

【学生问题】
宿舍空调坏了怎么报修？

请根据参考内容回答：
```

### 4.3 API 调用

```python
resp = requests.post(
    "https://open.bigmodel.cn/api/paas/v4/chat/completions",
    json={
        "model": "glm-4-flash",
        "messages": [
            {"role": "system", "content": SYSTEM_PROMPT},
            {"role": "user", "content": prompt},
        ],
        "max_tokens": 512,
        "temperature": 0.3,   # 低温度=回答稳定不发散
    },
)
```

- `temperature=0.3`：低温度确保回答稳定、不发散编造
- `max_tokens=512`：限制回答长度，校务问答不需要长篇大论
- 每篇参考文档截取前 800 字，避免超出模型上下文窗口

### 4.4 抽取式兜底

当 LLM 不可用（API Key 未配置/网络异常）时，自动降级为抽取式回答：

```
根据「校内日常服务电话」：后勤处日常服务电话：0756-7626267，
受理水电维修、家具报修等服务。

（另有 1 条相关依据，详见出处列表）
（当前为检索抽取式回答，大模型生成未启用时以此兜底）
```

抽取式逻辑：取 top-1 文档，按句号分句，找关键词命中最多的句子，原样拼接。

### 4.5 LLM 生成 vs 抽取式对比

| | 抽取式兜底 | LLM 生成 |
|---|---|---|
| 用几篇文档 | 1 篇 | top-K 篇综合 |
| 能否综合多篇 | ❌ | ✅ |
| 语气 | 公文原样 | 口语化（"学长告诉你"） |
| 复杂问题 | 答不全 | 能组织完整回答 |
| 速度 | 毫秒级 | 2-5 秒 |
| 花钱 | 0 元 | 0 元（智谱免费） |
| 准确性 | 不会编造 | 有幻觉风险（已用 prompt 约束） |

```json
  "topk": 5
}
```

**响应**：
```json
{
  "answer": "宿舍空调坏了可以打后勤处服务电话 0756-7626267 报修...",
  "confidence": 0.87,
  "references": [
    {
      "title": "校内日常服务电话",
      "department": "后勤处",
      "column": "日常服务",
      "source_url": "https://...",
      "score": 870
    }
  ]

```

### 5.3 处理流程

```
1. 接收 question
2. 调 hybrid_search() 混合检索 → top-K 文档
   ├─ 检索失败 → 降级为 keyword_search() 纯关键词
   └─ 仍无结果 → 返回兜底回答（建议联系部门）
3. 构建抽取式回答（兜底）
4. 若 LLM 可用 → 调 llm_generate() 生成回答，覆盖抽取式
5. 组装 references（出处列表）
6. 返回 AskResponse
```

## 9. 完整请求流程示例

以学生提问 **"宿舍空调坏了怎么报修？"** 为例：

```
[1] 关键词路（search.py）
    同义词扩展："空调"→["风扇","空调清洗"], "报修"→["维修","保修","故障"]
    FTS5 MATCH: "空调" OR "维修" OR "故障" → 3 篇命中
    LIKE 子串: "%空调%" OR "%报修%" → 5 篇命中
    合并打分 → top-5

[2] 语义路（embedding.py + vector.py）
    bge-m3("宿舍空调坏了怎么报修") → 1024 维向量
    与 286 篇文档向量算余弦相似度 → top-5

[3] RRF 融合（hybrid.py）
    两路结果按排名融合（K=60）
    两路都命中的文档分数叠加 → top-10 候选

[4] Rerank 精排（rerank.py）
    bge-reranker-v2-m3 对 10 篇候选逐一打分
    "维修服务流程" 0.95 > "日常服务电话" 0.87 > "设施管理办法" 0.41
    重排

[5] 时效降权（hybrid.py）
    2026 年通知 ×1.0, 2025 年 ×0.75, 更早 ×0.5
    final_score = (0.65×rerank + 0.35×rrf) × recency

[6] LLM 生成（llm.py）
    top-5 文档 + 问题 → GLM-4-Flash
    → "宿舍空调坏了可以打后勤处服务电话 0756-7626267 报修...
       （来源：后勤处-校内日常服务电话）"

[7] 返回（main.py）
    {
      "answer": "宿舍空调坏了可以打后勤处服务电话 0756-7626267 报修...",
      "confidence": 0.87,
      "references": [{ "title": "校内日常服务电话", "department": "后勤处", ... }]
    }
```

## 11. 降级策略

系统设计了多级降级，确保任何环节失败都能返回可用结果：

| 失败环节 | 降级方式 | 代码位置 |
|---|---|---|
| embedding 未配置/失败 | 纯关键词路检索 | `hybrid.py` 第 45-51 行 |
| reranker 失败 | 保持 RRF 排序不变 | `rerank.py` 第 36 行 |
| LLM 未配置/失败 | 抽取式回答（复制最相关句子） | `main.py` 第 109-127 行 |
| 混合检索异常 | 降级为纯关键词检索 | `main.py` 第 104-105 行 |
| 检索无结果 | 返回兜底回答（建议联系部门） | `main.py` 第 107 行 |
